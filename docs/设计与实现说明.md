# 双人早睡家庭 App：设计与实现说明

## 1. 产品边界

这是“两个人个人使用”的最小可运行版本，核心目标是低维护，而不是做通用社交产品。因此采用以下约束：

- 手机号作为稳定用户 ID，但当前没有密码、短信验证码和用户数据库。
- 手机号登录成功后，后端返回随机成员令牌；令牌保存在设备本地并用于日常 API。
- 一个家庭最多两个成员。
- 只允许编辑活动周；归档周只读。
- 后端单实例运行，一个家庭一个 JSON 文件。

这套边界比“所有数据都存在两部手机本地”多一个很小的 Go 服务，但能让两个人看到同一份数据，并避免数据库运维。手机号层为以后接短信验证码保留了稳定身份边界。

## 2. 使用流程

### 新建家庭

1. 填写后端地址，输入手机号并通过 `/ping` 测试。
2. 后端规范化手机号并确认这是尚未绑定的新用户。
3. 选择“新建家庭”，填写家庭名称和自己的称呼。
4. 后端生成家庭、创建者成员、邀请码和成员令牌。
5. 默认加载原始设计的工作日与周末计分表，创建者把邀请码发给另一人。

### 加入家庭

1. 另一台手机连接同一个后端并输入自己的手机号。
2. 手机号不存在时选择“加入家庭”，填写邀请码和称呼。
3. 后端确认手机号未占用且家庭未满两人后，生成第二个成员及令牌。

### 卸载重装或更换手机

1. 重新填写同一个服务器地址并输入原手机号。
2. 后端通过手机号找到原家庭和原成员。
3. 后端签发新的随机成员令牌，原设备令牌立即失效。
4. App 恢复原来的家庭、角色、记录和周报。

当前阶段手机号命中后直接签发令牌。未来启用短信验证码时，流程只是在第 2、3 步之间增加“验证码证明手机号控制权”，家庭与成员数据模型不需要重做。

## 3. 日期、打卡与周的定义

- “睡觉日期”代表这次睡眠所属的晚上。
- 默认凌晨 `06:00` 前打卡归到前一天晚上，例如周二 01:10 记为周一晚。
- 一周从周日开始，到周六结束；这里的日期均指“睡觉所属的晚上”。例如周一 01:10 属于周日晚，也属于周日开始的新周。
- 周五晚和周六晚使用周末规则，其余晚上使用工作日规则。
- 只保存原始时间 `HH:mm`，分数和罚金在读取时根据活动周规则计算。

保存原始时间而不把活动周分数写死，是“改规则后重算”复杂度较低的关键。设置修改后无需逐条改文件，只需使用新规则重新生成响应中的统计。

## 4. 周切换与归档

家庭文件只维护一个活动周，另有只读历史归档：

1. 按服务器当前时间的一键打卡直接写入活动周；手动补卡、编辑和删除在双人家庭中先生成待确认变更。
2. 打开 App 读取家庭数据或新一周第一次产生写操作时，自动切换活动周；若旧活动周有打卡或豁免，则计算完整快照并归档。
3. 新活动周继承旧周设置的副本，之后修改只影响新活动周。
4. 若旧活动周完全没有打卡，则不生成空归档。
5. 任何早于活动周的打卡、编辑或删除请求都拒绝。

从旧版周一制升级时执行一次边界迁移：把刚结束旧周中的周日记录、豁免及仍有效的待确认项移入“周日—周六”新活动周；旧周缩短为“周一—周六”并重新计算汇总。更早的历史周保持原范围，并通过周历版本字段继续兼容备份恢复。

归档保存当周设置快照、每日结果和汇总。因此以后调整积分不会篡改过去的周报。

### 双人确认与防作弊

- 手动补卡、修改时间和删除记录不会立刻覆盖原记录，而是保存为 `pendingChanges`。
- 待确认项包含日期、原时间、目标时间、操作类型、发起成员和创建时间。
- 发起人不能确认自己的变更；另一位成员同意后才写入原始打卡并重新计算本周，拒绝则直接移除待确认项。
- 一键“记录现在时间”使用服务器时间，直接生效并清理同日未完成的手动修改申请。
- 同一成员同一天只保留一个待确认项；重新提交会替换之前的申请。
- App 打开期间每 10 秒轻量刷新一次家庭视图，并在重新回到前台时立即刷新；收到对方申请后，记录导航出现角标并显示确认卡片。当前无系统推送服务，因此 App 完全关闭时不会发送安卓通知。
- 顶部同步标记显示“同步中”“离线”或最近一次成功同步时间。页面进入后台时停止轮询，网络恢复或回到前台时立即拉取，避免无意义的后台请求。
- 周切换时未处理的旧周申请会被清理，不进入历史归档。
- 单人家庭没有可确认的第二人，手动操作保持直接生效。

### 特殊情况豁免

- 每位成员每自然月最多使用 2 次，双人家庭由本人申请、另一位成员确认；申请人不能确认自己的申请。
- 豁免通过后会覆盖当天的普通打卡结果：当天计为有效记录，积分与罚金均为 0，但不计入平均入睡时间和睡眠折线。
- 同一成员同一天重复申请会替换原待确认申请；豁免通过时会清理该日尚未确认的普通打卡修改。
- 周切换时，已通过的豁免随每日结果和设置一起冻结进历史归档；未处理申请会被清理。
- 月度上限同时统计当前活动周和历史归档，因此跨周后仍不会重复获得额度。
- 记录页为双方分别显示本月已通过、待确认和剩余次数；待确认申请会预占额度，拒绝后自动恢复。

## 5. 默认计分

推荐值完全取自原始设计：

| 截至时间 | 工作日积分 | 工作日罚金 | 周末积分 | 周末罚金 |
|---|---:|---:|---:|---:|
| 22:30 | +3 | 0 | +5 | 0 |
| 23:00 | +2 | 0 | +4 | 0 |
| 23:30 | +1 | 0 | +3 | 0 |
| 00:00 | 0 | 0 | +2 | 0 |
| 00:30 | -1 | 20 | +1 | 0 |
| 01:00 | -2 | 50 | 0 | 0 |
| 01:30 | -3 | 100 | -1 | 20 |
| 更晚 | -3 | 100 | -2 | 50 |

时间边界使用“截至且包含”。积分以相邻两个档位为锚点，按实际入睡分钟线性计算并四舍五入到一位小数，例如 23:00 为 2 分、23:30 为 1 分时，23:05 为 1.8 分、23:20 为 1.3 分。罚金仍按整档计算：23:01～23:30 使用“截至 23:30”一档的罚金。最后一档“更晚”从上一档截止时间后的第一分钟立即生效，例如最后边界为 01:30，则 01:31 进入“更晚”档。创建者可以编辑所有锚点、分数和罚金，积分与罚金均允许负数；时间边界必须严格递增，最后一档固定为“更晚”。

### 内置奖励计算

奖励规则包含个人档位、双人合计档位和付款关系，已不适合使用自由文本编辑。App 改为内置规则，并直接根据周报中已有的个人总分计算参考金额：

- 个人至少有 5 个有效记录日且达到 5 / 10 / 15 / 20 分时，分别奖励 20 / 40 / 70 / 100 元，由对方转入共同账户；豁免日计入有效记录但保持 0 分。
- 两人都达到个人门槛后，双人合计达到 10 / 20 / 30 / 40 分时，分别追加 20 / 40 / 70 / 100 元，由两人各承担 50%。
- 个人奖励每人最高 100 元，双人累计奖励最高 100 元，每周积分奖励合计最高 300 元。
- 300 元上限不包含罚金；罚金流向沿用原始设计，与积分奖励分开结算。

周报直接展示当周奖励参考总额、每人的个人奖励、付款人和双人累计奖励。实际转账和确认由双方线下手工完成，App 不保存已结算状态、账户流水或结算快照。原周报 info 弹窗中的等级说明移至“设置 → 等级说明”；“设置 → 奖励规则”使用两张内置表格展示规则。这两个查看入口对所有家庭成员可见；计分档位编辑仍只对创建者可见。

后端仍保留 `rewardNote` 字段用于兼容旧家庭文件和已归档数据，新版 App 不再读取或编辑它。活动周同时保存 `rewardRuleVersion`；归档时冻结该版本，前端按版本选择内置奖励档位，因此未来调参不会改写旧周奖励参考。现行版本为 `v4`；已有活动周升级到 `v4` 并按分钟重新计算，缺少版本的历史归档按 `v3` 保留。

## 6. 当前统计

活动周与每个归档周均提供：

- 每人总积分、总罚金、打卡天数和平均入睡时间。
- 两人合计打卡数。
- 当前活动周完成率：`合计打卡数 / (家庭成员数 × 截至今天已进行天数)`，取整数百分比，避免周中因未来日期尚未打卡而虚低。
- 历史归档周完成率仍为：`合计打卡数 / (家庭成员数 × 7)`，保持完整周口径。
- 每日双方入睡时间、积分、罚金和记录来源。
- 豁免日作为有效记录计入打卡天数和完成率，但固定为 0 分、0 罚金，并从平均入睡时间与折线图中排除。
- 双方每日入睡时间折线图；纵轴按夜间连续时间展示，凌晨时间排在午夜之后。图表使用“越靠上越晚、越靠下越早”的方向，并显示理想入睡目标线。
- 双人总分与个人总分等级。个人使用“个人得分 / 个人理论最高分”，双人使用“两人总分 / 两人理论最高分之和”；归档周使用当周冻结的规则计算理论最高分。

| 等级 | 得分比例 | 当前含义 |
|---|---:|---|
| 晨光 | `>= 80%` | 状态闪闪发光 |
| 新芽 | `>= 55%` | 节奏稳定生长 |
| 清风 | `>= 25%` | 正在靠近目标 |
| 守夜 | `>= 0` | 再早一点就好 |
| 重启 | `< 0` | 下周轻轻重来 |

等级当前只做展示。系统会计算并展示奖励参考金额和付款关系，但不生成共同账户流水、结算确认或实际转账。

周报页面只让本周使用完整看板。历史周默认显示日期、双人积分、完成度、奖励参考和双方积分摘要，点击后展开该周完整详情；同一时间最多展开一周。

当已有上一周归档且本周至少产生一条有效记录时，周报在完整看板前显示紧凑的同期比较。系统按本周已进行的星期天数截取上周相同范围，只比较双人积分和双方平均入睡时间，避免用未结束的本周直接对比完整上周。

罚金当前只做统计，不处理支付。原始规则中的“给对方还是共同账户”属于线下结算约定。

### 30 天规则复盘

- 设置页持续显示本轮周期进度，到期后提示双方共同复盘。
- 二级页面按当前周期汇总双人完成度，以及每人的有效记录天数、积分、罚金、豁免次数和平均入睡时间。
- “首 7 天”和“最近 7 天”仅使用非豁免的真实入睡记录计算平均时间，用于观察变早、稳定或变晚趋势。
- 任一成员少于 7 天有效记录时，页面明确提示趋势数据仍不足，避免过早解读。
- 奖励部分只合计完全落在周期内的完整周参考金额，避免把周期边缘的不完整周误算为整周奖励。
- 复盘完成后由创建者开始新的 30 天周期；该操作不生成账单，不代表奖励或罚金已经结算。

## 7. 文件数据设计

默认目录为 `./data`，每个家庭保存为：

```text
data/
├── fam_xxxxx.json
└── fam_xxxxx.json.bak
```

家庭文件包括：

- 家庭 ID、名称、时区、邀请码及其摘要。
- 两个成员的 ID、称呼、角色、规范化手机号、预留的验证时间和令牌摘要。
- 当前活动周的起止日期、周历版本、规则与原始打卡。
- 当前活动周奖励规则版本，以及已冻结的历史周计分和奖励版本快照。
- 当前活动周尚未确认的手动变更。
- 当前活动周已通过的豁免、待确认豁免和 30 天复盘周期起点。
- 版本号和递增修订号。

写入步骤是“写 `.tmp` → 备份旧文件为 `.bak` → 原子替换正式文件”。单进程内用互斥锁串行写入，足以覆盖两人自用负载，也避免并发请求互相覆盖。

### 家庭数据导出与恢复

- 所有成员都可导出一份格式化 JSON；内容包括计分规则、当前周、历史周、豁免、待确认项和复盘周期。
- 导出时移除成员令牌摘要和邀请码摘要，但保留恢复所需的家庭邀请码、手机号及习惯记录，因此文件仍属于敏感个人数据。
- 只有创建者可以恢复；后端只接受相同家庭 ID、相同成员集合、受支持格式版本且结构合法的备份。
- 恢复使用备份中的业务数据，但保留后端当前手机号、角色、验证状态和成员令牌，所以双方无需重新登录。
- 恢复同样走原子写入并保留恢复前的 `.bak` 文件。它不是自动云备份，仍需双方自行保管导出文件。

后端启动时会把 `DATA_DIR` 转成绝对路径并写入日志。部署时仍应显式传入固定的绝对路径，避免从不同工作目录启动而产生多套 `./data`。

## 8. 架构

```text
Android App (React + Capacitor)
             │ HTTP/JSON + Bearer token
             ▼
Go HTTP API (标准库 net/http)
             │
             ├── 计分、活动周、归档规则
             │
             └── JSON 文件 + .bak
```

前端和后端源码位于同一个项目，但运行时仍是两个进程：Android App 是客户端，Linux 可执行文件是服务端。后端不内嵌网页，也不提供浏览器登录页面。

## 9. 安全与部署取舍

- 随机成员令牌相当于设备凭证，泄露后应视为身份泄露；手机号重新登录会轮换令牌。
- 文件中保存规范化手机号和家庭邀请码，令牌只保存 SHA-256 摘要。数据目录必须保持私有权限并纳入备份保护。
- 当前 `verificationRequired=false`，手机号只代表用户声明身份。该模式只适合可信私人网络，不应直接用于公开服务。
- 接入短信后，应增加验证码有效期、单号码/单 IP 频率限制、尝试次数限制和一致化响应，降低枚举与撞库风险。
- JSON 文件权限为 `0600`，数据目录创建权限为 `0700`。
- 局域网自用可使用 HTTP；跨公网必须加 HTTPS，并限制服务端口访问。
- 文件后端只支持单个服务进程。不要同时启动多个实例共享同一个数据目录。

## 10. 刻意不纳入最小版本的功能

共同账户奖励由 App 使用内置规则计算参考金额，月度双人确认豁免和 30 天复盘提醒已进入当前数据模型。账户流水、结算快照、已结算确认和实际转账刻意不实现，继续由双方手工处理。完整原始设想仍保留在 `双人早睡习惯挑战_原始规则.md`。

若继续扩展，推荐顺序是：

1. 短信验证码和发送频率限制。
2. HTTPS、反向代理和自动备份脚本。
3. 可选的加密备份或系统分享能力。

只有双方之后明确需要时，再评估共同账户流水和自动结算；它们不属于当前路线图。
